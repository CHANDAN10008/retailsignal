# RetailSignal

**Retail ETL, customer churn modelling, and demand planning**  
Python · pandas · scikit-learn · R · PostgreSQL · Streamlit · AWS-ready design

RetailSignal is a reproducible portfolio project that turns messy retail transactions into an analysis-ready dataset, compares four churn classifiers, evaluates a demand forecast on a chronological holdout, and presents the results in an interactive dashboard.

> **Data note:** Every row is generated by the project for demonstration. It contains no real customer information. Model scores and statistical findings are illustrative and must not be presented as results from a real retailer.

## What it does

- Generates deterministic synthetic customer and transaction CSVs with missing values and duplicate transaction IDs.
- Validates and cleans transaction fields, removes duplicate IDs, calculates net sales, aggregates customer behaviour, and writes a quality report.
- Compares logistic regression, decision tree, random forest, and gradient boosting with a stratified holdout. Reports accuracy, precision, recall, F1, and ROC AUC, then saves the top model and feature importance.
- Forecasts three months of category-level demand with gradient boosting and lag features. The final six observed months are held out for MAE, RMSE, and MAPE evaluation.
- Runs R summaries, Spearman correlations, and a Welch two-sample comparison of sales by the synthetic churn label.
- Includes a dark Streamlit dashboard, a PostgreSQL schema and example queries, and a container definition.

## Quick start (Windows PowerShell)

```powershell
cd RetailSignal
py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -e .
python -m retailsignal.cli all
streamlit run app.py
```

Open the local URL shown by Streamlit. The dashboard can also generate its demo inputs and modelling outputs the first time it starts. To rebuild from scratch in the dashboard, use **Rebuild synthetic demo**.

The pipeline stages can be run separately:

```powershell
python -m retailsignal.cli generate
python -m retailsignal.cli etl
python -m retailsignal.cli train
python -m retailsignal.cli forecast
```

`train` expects the processed customer table; `forecast` expects the processed monthly demand table. Run `all` once first when starting with a clean checkout.

## R analysis

After running the Python ETL, install R and run:

```powershell
Rscript r/eda.R
```

The Welch test compares average lifetime net sales for the generated churn classes. It describes a difference in this synthetic sample; it does not imply that churn causes lower sales or that a business action would change churn.

## PostgreSQL

`sql/schema.sql` defines tables for customers, transactions, and monthly demand. Create a database, apply the schema with `psql -f sql/schema.sql`, and load the generated CSVs using PostgreSQL `\copy` from the repository root. For example:

```sql
\copy retailsignal.customers FROM 'data/processed/modelled_customers.csv' WITH (FORMAT csv, HEADER true)
\copy retailsignal.transactions FROM 'data/processed/clean_transactions.csv' WITH (FORMAT csv, HEADER true)
\copy retailsignal.monthly_demand FROM 'data/processed/monthly_demand.csv' WITH (FORMAT csv, HEADER true)
```

These tables are intended as an analytical mart. `sql/analysis_queries.sql` has sample churn-segment, category-demand, and sales queries.

## AWS deployment blueprint

This repository is **not deployed to AWS** and does not create cloud resources. A practical production path would put raw files in S3, run scheduled transforms with Glue or ECS tasks, store curated tables as Parquet in S3 and query them with Athena, then host the Streamlit container on ECS Fargate behind an HTTPS load balancer. Use IAM roles for access and CloudWatch for logs and health checks. Add account, networking, retention, and cost controls before provisioning. The included Dockerfile only packages the dashboard; it does not provision AWS infrastructure.

Build and run the container locally:

```powershell
docker build -t retailsignal .
docker run --rm -p 8501:8501 retailsignal
```

## Modelling notes and limits

- The churn target is generated from a known synthetic probability rule. This intentionally creates a learnable example; the resulting feature ranking is not evidence about real customers.
- A random stratified split is used for the static churn classification example. A real deployment needs a time-aware split, leakage review, calibration, fairness checks, monitoring, and a documented decision threshold.
- Demand features use prior months, and the final six actual months are excluded from model fitting. Forecast uncertainty is not estimated; do not use the sample output for purchasing or inventory commitments.
- `churned` is a demo label, not an operational definition. Real work would first agree on the churn window, observation date, and label with business stakeholders.
